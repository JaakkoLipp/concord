### 10. Server tags

As on Discord: a server can have a short tag with a badge, such as "SLOP", and a member can wear it next to their name everywhere.

**Stoat has no place for it.** Synced settings are private to the account. The public user fields are the display name, pronouns, status and bio, and hiding a tag in one of those would break that field and show as junk in Stoat's own client. So tags are the first feature on Concord's own layer (architecture section 11, built in M4.4). They use its session check, gates and store, and add only their own tables and endpoints.

**Built**:
- **The tables**, in the layer's store:
  - a server's tag: up to 4 characters and one of the server's custom emoji as the badge,
  - which tag a user wears.
- **The API**, under `/app/api/v1/tags`:
  - Reading is open to signed-in users, in bulk by user ID, so a member list costs one request.
  - Clients refetch on open, every 60 s and on focus, so a change shows within a minute.
  - Each client shows a tag only for people in its own member list, so a departed member's tag disappears at once. The layer removes stale rows on its next write.
- **Who may enable a tag for a server**: the same permission as creating servers. The caller must be in `restrict_server_creation` in Stoat's `GET /api/`, and hold Manage server in that server. Today that is Jaakko alone.
- **Wearing**: any member of a server with a tag can choose it in profile settings, or choose none. Membership is checked when choosing.
- **Shown**: next to the name in messages, the member list, the profile popout and the DM list. Clicking it shows the server, as in the reference.
- **Ending**:
  - leaving or being removed from the server stops the tag showing on the next check,
  - disabling a server's tag removes it from everyone.

**Done when**:
- `dev-admin` enables a tag on a seeded server, and `aino` chooses it.
- `dev` sees it next to aino's name in messages and the member list.
- `dev`, who isn't allowed to create servers, gets 403 trying to enable a tag over the API.
- After aino leaves the server, the tag no longer shows.

## Decisions

Each is a recommendation that sign-off accepts unless you say otherwise.

1. **GIPHY through Concord's own layer, no new service.**
   - The beta key's hourly limit is shared by everyone. Task 1 measures it.
   - A plain Caddy route would be open to anyone on the internet, who could use up that limit, and stock Caddy has no rate limiter. The layer adds the session check, per-user limits and a cache.
   - If it's too low, GIPHY's production key needs an application with screenshots.
2. **Restart LiveKit only on a renewed TURN certificate.** It is in the repo since M4. Sign-off applies it to production with `pnpm deploy:stack:prod`.
3. **Streams start unwatched**, as on Discord. This saves the VPS's upload, which five viewers of a 1080p60 share would otherwise take at about 8 Mbps each.
4. **Out of M4.5**:
   - threads, forwarding, bookmarks, reminders, apps, soundboard, activities and stickers: Stoat doesn't have them,
   - push-to-talk with another window focused: M5,
   - server-wide search: decision gate criterion 2.
5. **Server tags on Concord's own layer** (task 10, after M4.4). The alternatives misuse a public Stoat field, which breaks that field and shows junk in Stoat's own client.
6. **Order**: M4.5's tasks other than 7 and 10 can start now. It is client-side and mostly survives a change of backend. The voice evening still decides decision gate part B.
