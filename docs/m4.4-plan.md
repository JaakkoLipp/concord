## Tasks

### 1. Probes

**What they confirm**:
- `http://api:14702` from inside `concord-web`, on the local stack and on production, read-only.
- How long `GET /users/@me` takes on the internal network.
- That a `VACUUM INTO` copy taken while writing is consistent, and how long it blocks Node's event loop.
- That the host's `concord/data/` can be made writable for the container's user.

**Done when** each answer is in m4.4-results.md.

### 2. The core, server side

**Built**, in `apps/web/src/lib/server/layer/`:
- **The session check**:
  - a bounded cache: 60 s for good answers, 10 s for bad,
  - a per-address limit before any Stoat call,
  - 503, never 401, when Stoat fails.
- **The permission check**, through `packages/domain`'s calculator, cached 30 s, at most two Stoat calls per write. Plus the server-creator and admin gates.
- **Input checks**: ULID-shaped IDs, normalised text measured in visible characters.
- **The store**:
  - `node:sqlite` in WAL mode, with numbered migrations,
  - a copy of the file before migrating,
  - a refusal to start against a newer database.
- **Per-user rate limits**.
- **Endpoints**:
  - `GET /app/api/v1/me`: who you are, and which gates you pass,
  - `GET /app/api/v1/health`,
  - `GET /app/api/v1/check/{server}`: a harmless, permission-gated endpoint that answers whether you hold Manage server there, so live checks can show a Stoat permission being enforced.
- **On the client**: a `Layer` interface in `packages/domain`, as `Backend` is for Stoat. Its implementation signs out only on the layer's own 401.

**Done when** unit tests cover:
- the session check: none, bad, expired, cached, good, and Stoat failing,
- each gate,
- the migrations on an empty and an existing file, and the newer-database refusal,
- the input checks,
- the rate limits.

### 3. Live check and operations on the local stack

**Built**:
- **Mounts**: the read-write mount for `concord/data/`.
- **Container environment**: `ADMIN_USER_IDS` in the compose file's `environment:`.
- **Backups**: `backup.sh` takes a `VACUUM INTO` copy first, without failing the rest, and saves the copy, not the live files.
- **`tools/live/src/layer.ts`**:
  - `/me` with and without a session,
  - `check/{server}` for a persona with and without Manage server,
  - a flood of bad tokens hitting the per-address limit, not Stoat,
  - a persona hammering its own server in the client while the check runs, without a 429 in the client.
- **Docs**:
  - dev-environment.md,
  - vps-runbook.md, including section 7's restore drill.

**Done when**:
- `layer.ts` passes,
- the store survives a redeploy,
- a backup holds the copy, and restoring it into a fresh folder opens with the same rows,
- a build with a newer migration refuses an older one's rollback.

## Decisions

Each is a recommendation that sign-off accepts unless you say otherwise.

1. **In `concord-web`, not a new service.** It is one less container to run, and it already has the network access. If the layer outgrows it, it can split out later, because the endpoints don't depend on SvelteKit's pages.
2. **SQLite through `node:sqlite`.** No dependency, one file and easy backups, which is enough for 200 people. Postgres comes only with a backend of our own.
3. **A token header, not cookies.** There is no cross-site request forgery to defend against.
4. **Polling first, no live stream yet.** Clients fetch on open, every 60 s and on focus. Tags change rarely, and a stream brings reconnect storms on every deploy, long-lived sessions to re-check, and Caddy buffering. It comes when a feature needs sub-second updates.
5. **The admin panel reads no database.** Its lists come from a root cron snapshot, as its status page does. Its plan, in another session, moves onto `/app/api/v1/admin/*` and this layer's session check and admin gate.
6. **Order**: M4.4 before M4.5, as approved. M4.5's tasks 1 to 9 don't need the layer, so they can start as soon as M4.5 is signed off. Only task 10, server tags, waits for M4.4.
