## Tasks

### 1. Probes

**What they confirm**:
- `http://api:14702` from inside `concord-web`, on the local stack and on production, read-only.
- A streamed response from a `+server.ts` endpoint reaches the browser through Caddy without being buffered.
- How long `GET /users/@me` takes on the internal network, which sets the cache's value.
- That a `VACUUM INTO` copy taken while writing is consistent.

**Done when** each answer is in m4.4-results.md.

### 2. The core, server side

**Built**, in `apps/web/src/lib/server/layer/`:
- The session check with its 60 s cache, and errors shaped as `{type}`.
- The permission check, through `packages/domain`'s calculator, plus the server-creator and admin gates.
- The store: `node:sqlite`, numbered migrations in `apps/web/src/lib/server/layer/migrations/`, and a version table.
- Per-user rate limits.
- `GET /app/api/v1/me` (who you are, and which gates you pass) and `GET /app/api/v1/health`.

**Done when** unit tests cover:
- the session check: none, bad, expired, cached and good,
- each gate,
- the migrations on an empty and an existing file,
- the rate limits.

### 3. Live events and the client side

**Built**:
- `GET /app/api/v1/events`, a streamed response with a heartbeat every 25 s.
- On the client, a `Layer` interface in `packages/domain`, as `Backend` is for Stoat. Its implementation reads the stream with `fetch`, reconnects with backoff, and fetches again after a reconnect.

**Done when** a live check, `tools/live/src/layer.ts`, shows on the local stack:
- a test event written for one persona reaches another persona's open client within a second,
- the stream comes back after `concord-web` restarts.

The test event is a write endpoint that exists only while `.allow-wipe` does.

### 4. Operations on the local stack

**Built**:
- the read-write mount for `concord/data/`,
- `backup.sh` taking a `VACUUM INTO` copy before restic,
- `ADMIN_USER_IDS` in `host.env`,
- docs: dev-environment.md, vps-runbook.md, and section 7 of the runbook for the restore drill.

**Done when**:
- the store survives a redeploy,
- a backup holds it, and restoring it into a fresh folder opens with the same rows.

### 5. Production

**Built**: `pnpm deploy:stack:prod` and `pnpm deploy:web`. Then the backup by hand, as M3 did.

**Done when**:
- `pnpm live:prod tools/live/src/routes.ts` passes, extended with `/app/api/v1/health`,
- `/app/api/v1/me` answers 401 without a session,
- Jaakko's session gets 200 from `/app/api/v1/me` in the browser,
- the nightly backup holds the file.

### 6. Review

A Sonnet review of the diff, looking mainly at the session check, the gates, and anything that touches Stoat's network. Findings are fixed or recorded.

## Decisions

Each is a recommendation that sign-off accepts unless you say otherwise.

1. **In `concord-web`, not a new service.** It is one less container to run, and it already has the network access. If the layer outgrows it, it can split out later, because the endpoints don't depend on SvelteKit's pages.
2. **SQLite through `node:sqlite`.** No dependency, one file and easy backups, which is enough for 200 people. Postgres comes only with a backend of our own.
3. **A token header, not cookies.** No cross-site request forgery to defend against. The cost is a streaming `fetch` instead of `EventSource`.
4. **Order**: M4.4 before M4.5, as approved. M4.5's tasks 1 to 9 don't need the layer, so they can start as soon as M4.5 is signed off. Only task 10, server tags, waits for M4.4.
