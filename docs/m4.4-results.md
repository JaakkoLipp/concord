## Task 1: probes, 2026-10-15

On the local stack, from inside `concord-web`. The probe scripts were throwaway, in the scratchpad.

| Question | Answer |
|---|---|
| Reaching Stoat | `http://api:14702/` answers 200 from `concord-web`. Production runs the same compose file for `concord-web`, so the layer's `/health` reports Stoat's reachability, and task 4's `routes.ts` confirms it there without a separate SSH probe. |
| The server-creator list | In `GET /` under `features.limits.global.restrict_server_creation`, where the client already reads it. |
| `GET /users/@me` on the internal network | 1.9 ms median, 2.8 ms at p90, over 30 calls. A bad token gets 401 with an HTML body, so the layer reads only the status. It counts against the user's own bucket of 20 per 10 s, which the 60 s cache keeps to one call a minute per user. |
| `node:sqlite` in the image | Loads in `node:24.21.0-alpine` with no flag and no warning. |
| A `VACUUM INTO` copy while writing | Three copies taken by a second process while another committed about 38,000 transactions a second. Each passed `integrity_check` and held whole transactions only: every row pair complete and a moved balance summing right. The copy is a single file, not in WAL mode. Copying 36 to 106 MB took 95 to 230 ms, and the writer's longest pause was 33 ms. The layer's real data will be kilobytes. |
| A writable `concord/data/` | The container's `node` user is uid 1000, as is `jaakko` on this machine, and a bind-mounted folder is writable. The VPS user's uid isn't recorded, so the stack deploy creates the folder owned by uid 1000, with `sudo` on production. |

**Decided from these**:
- The backup copy runs as a one-off `node` process through `docker exec`, as the plan now says. It doesn't block the server, so the event-loop question fell away.
- `deploy:stack`'s copy of `deploy/` excludes `data/` too, though it never deletes anything, so that no later change to it can touch the store.
