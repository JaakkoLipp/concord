## Task 2: the core, 2026-10-15

Built in `apps/web/src/lib/server/layer/`, with `/app/api/v1/health`, `/me` and `/check/{server}`, and the `Layer` interface in `packages/domain` with its client in `apps/web/src/lib/layer/`. 34 unit tests cover the session check, the gates, the permission check, the store's migrations, the input checks, the limits and the client's sign-out rule.

**Choices made while building**:
- **A known token skips the per-address limit.** A token seen good in the last hour isn't counted, so a flood of random tokens from one address, or one NAT, can't lock out the people already signed in behind it. Only unknown tokens spend the limit of 20 lookups a minute.
- **Concurrent checks of one token share one Stoat call**, so a redeploy, which empties the cache, doesn't send every open client to Stoat at once.
- **Stoat's 429 is passed on as a 429.** `GET /users/@me` uses the caller's own bucket, which their client shares, and a limit must never read as a bad session.
- **Both gates fail closed.** An empty `ADMIN_USER_IDS` makes nobody admin. An empty server-creator list passes nobody, though Stoat itself reads an empty list as "everyone". An `ADMIN_USER_IDS` entry that isn't a user ID stops the layer from starting.
- **A layer that can't start doesn't take chat down.** If the store can't open, because the data folder is missing or the database is newer than the build, the layer logs `layer: NOT STARTED`, its endpoints answer 503 `LayerUnavailable`, and `/app` is still served. The plan said the server refuses to start. This keeps the data just as safe, and it means an `/app` deploy that reaches production before the stack change can't take the client down.
- **The client shows the gates** in one read-only line in the settings sidebar, above Log out, for anyone who passes one. It is fetched once at sign-in. If the layer is down, the line is left out and nothing else changes.

The copy, put alone into a fresh folder as `layer.db`, opened in a new container with the same rows and passed `integrity_check`. `backup.sh` itself runs only as root on the VPS, with restic, so task 4's nightly run checks that part. |
| A newer database refuses an older build | A build with a probe migration 2 copied version 1 to `layer.db.before-v2` and migrated. The older build then logged `layer: NOT STARTED: the store is at version 2, newer than this build's 1`, `/health` answered 503 `LayerUnavailable`, and `/app` still answered 200. Following the runbook's rollback, putting `before-v2` back, brought the layer up with its rows. |

**Found: a client saturating its own Stoat bucket gets 429s without the layer too.** The check first clicked through server settings as fast as it could, about 18 Stoat calls for the server in 25 s. Run twice as a control without any layer calls (`LAYER_CHECK_MS=0`), the client still got 429s from Stoat on `members` and `bans`, which its queue retries. So "no 429 while hammering" can't pass whatever the layer does. The check now moves through a section every 4 s for a minute while the layer checks every 3 s: 9 server calls from the client and 18 layer checks, with no 429 anywhere. The layer's lookups take at most 2 of the caller's 5 calls per 10 s, once every 30 s per server, as architecture section 11.2 says. On a client already at its limit, that can mean one more retried 429. Writes that need a permission check, such as enabling a server tag, are rare.

**Seen locally**: every request reaches `concord-web` from Docker's gateway, `172.20.0.1`, so locally the per-address limit is one shared limit. On production, Caddy passes the real address on.
