# M4.8 results

## 0. Probes

Run on 2026-10-16 against the local stack (Stoat 0.15.5) with two throwaway accounts made by `pnpm seed account` (`probe48`, `probe48x`). No existing persona was touched. TOTP was added to `probe48` and removed again, and every session the probes made was revoked. The two accounts themselves stay (the API can't delete them without a mail link). Their leftovers: `probe48` has recovery codes active and a pending, unverified email change.

### 1. Banner timing

`setOffline(true)` does **not** close the open WebSocket. The browser fires the window `offline` event within 1 to 4 ms (`navigator.onLine` is false), but the socket only dies when the ping check gives up. Three runs, started at different points in the 20-second ping cycle:

| Run | Socket closed | UI shows "Reconnecting…" |
|---|---|---|
| 1 | 25.4 s | 24.7 s |
| 2 | 18.9 s | 18.1 s |
| 3 | 13.4 s | 12.9 s |

So the wait is 10 to 30 s (ping every 20 s plus a 10 s pong timeout). Going back online is fast: `Connected` again 105 ms after `setOffline(false)`, because `socket.ts` already listens for `online`. Nothing listens for `offline`.

The status text lives in the user dock popover (`p.connection`), and `store.connection` moves to `reconnecting` in step with it.

**Plan impact:** yes. Task 6 needs a `window` `offline` listener that shows the banner at once (and `online` clears it when the store is `ready`). Shorter ping times are not needed for that case. Keep the ping check for a dead server or a blocked network where the browser still says online.

### 2. MFA ticket (`x-mfa-ticket`)

A ticket comes from `PUT /auth/mfa/ticket` with one of `{password}`, `{totp_code}` or `{recovery_code}`. Which method works depends on whether TOTP is on:
- TOTP off: `{password}` works.
- TOTP on: `{password}` gives 400 `DisallowedMFAMethod`. Use a TOTP or a recovery code. A recovery code is used up by making a ticket. A TOTP code can't be reused inside its 30 s window.
- Before recovery codes exist, the allowed methods are only `Totp`. After they are generated they are `Totp` and `Recovery`.

What needs a ticket (401 without one):

| Action | TOTP off | TOTP on |
|---|---|---|
| `DELETE /auth/session/{id}` | ticket needed | ticket needed |
| `DELETE /auth/session/all` | ticket needed | ticket needed |
| `PATCH /auth/account/change/password` (with `current_password`) | no ticket | ticket needed |
| `PATCH /auth/account/change/email` (with `current_password`) | no ticket | ticket needed |
| `POST /auth/mfa/totp` (make a secret) | ticket needed | n/a |
| `PUT /auth/mfa/totp` (enable, `{totp_code}`) | no ticket (204) | n/a |
| `DELETE /auth/mfa/totp` (disable) | n/a | ticket needed |
| `POST /auth/mfa/recovery` (fetch codes) | n/a | ticket needed |
| `PATCH /auth/mfa/recovery` (regenerate) | not tested | ticket needed |
| `PATCH /auth/session/{id}` (rename) | no ticket (200) | not tested |

Notes:
- Session revoke needs a ticket **even without TOTP**. The ticket then comes from the password.
- **A ticket is single use.** Reusing it gives 401 (tested on session revoke, recovery fetch and regenerate). Revoking two sessions or doing two actions means two tickets.
- Fetching recovery codes before any were generated returns an empty list. They must be regenerated first (`PATCH`), which returns 10 codes.
- **A password change does not log out the other sessions** (tested with TOTP off and on: the other sessions' tokens still worked). The reset-password flow is the one that has `remove_sessions`.

**Plan impact:** yes, for tasks 8 and 9. Session revoke always needs a "confirm your password" step (or a TOTP code when TOTP is on). Password and email change need one only when TOTP is on, so the dialog must ask for a code in that case. The UI should keep the "confirm" step as a shared helper that returns a fresh ticket per action. The "also log out other devices" wording on password change needs an explicit revoke-all with a second ticket, or should be dropped.

### 3. Cold-start mentions in DMs and groups

`GET /sync/unreads` for DMs and groups lists **every** message from someone else under `mentions`, whether or not it mentions you, and in a group also a message with `@everyone`. That matches the live rule (`mentionsSelf` returns true for any DM or group message). In a server text channel only the direct mention was listed, matching the live rule. The sender's own messages produce no entry for the sender.
- Entries appear a moment after the post (not in the first 1.5 s, all there later). The order in the list isn't sorted.
- Not tested: @everyone and role mentions in a server channel (the throwaway account may not use @everyone there: 403). The existing plan note stands: cold-start counts can't say why a message counted.

**Plan impact:** no.

### 4. Single message fetch

`GET /channels/{c}/messages/{id}` returns 200 with one plain message, in text channels and DMs. Keys: `_id, nonce, channel, author, content, mentions`. The author is an ID only. There is no `user` or `member` object, and `?include_users=true` changes nothing. Only the list endpoint wraps `{messages, users, members}` with that flag. So a "jump to a message" or inbox row has to find the author in the store or fetch it separately.

**Plan impact:** small. Wherever the plan fetches one message, add a user lookup, or fetch via the list endpoint with `include_users` (for example `?nearby=` or `?limit=1&before=` style) when the author may be unknown.

### 5. Email change

Local (Mailpit, `features.email` is true): the `PATCH` returns 204 and the account email is **not** changed yet. A "Verify your account" mail goes to the **new** address with a `/login/verify/<token>` link. After `POST /auth/account/verify/<token>` (200) the account has the new email, the old email no longer logs in, and the current session stays valid. With TOTP on, the change needs a ticket (section 2).

Production (read-only): `docs/m3-plan.md`, `docs/vps-runbook.md`, `docs/architecture.md` and `deploy/revolt-changes.md` agree that production runs with `[api.smtp] host = ""`, so no mail is sent and accounts are created already verified; real email waits for M6. I could not call production, so what an email change does there is **inferred, not tested**: with verification disabled Stoat most likely applies the change at once, but I haven't seen it. The reliable switch is `features.email` from `GET /api/` (true locally; it should be false on production).

**Plan impact:** yes. Show the email form only when `features.email` is true, or label it clearly. Do not promise "applies at once" or "check your mail" without checking that flag. Have Jaakko or a later task test it on production before enabling it there, or leave it to M6.

### 6. Identifying "this device"

Not possible for a browser that is already signed in. `GET /auth/session/all` returns only `_id` and `name` for each session: no token, no `last_seen`, no origin. The WebSocket `Authenticated` and `Ready` events carry no session ID either, and there is no `GET /auth/session/current`. The client stores only the token (IndexedDB). The login response **does** return the session `_id` (also `name`, `last_seen`, `origin`).

So: store the `_id` from the login response from now on. For browsers that are already signed in, "This device" needs a fallback. The sessions all have the name `Concord`, so "newest session with that name" is only a guess and is wrong if another device signed in later. A safer fallback is to show no "This device" mark for those browsers until the next sign-in, or to ask them to sign in again once.

**Plan impact:** yes, task 8: save the session ID at login, and don't promise a "This device" label for existing logins.

### 7. Autumn and audio files

Uploads to `/autumn/attachments`, then posted as message attachments to read the metadata:

| File | Uploaded as | Result |
|---|---|---|
| audio-only WebM/Opus | `audio/webm`, `video/webm`, `audio/webm;codecs=opus`, octet-stream | `content_type video/webm`, metadata **File** |
| Ogg/Opus (also `.opus`) | `audio/ogg` (with or without codecs) | `audio/opus`, metadata **Audio** |
| Ogg/Vorbis | `audio/ogg` | `audio/ogg`, metadata **Audio** |
| WebM with video (control) | `video/webm` | metadata **Video** (width, height) |

So Autumn does **not** call an audio-only WebM Audio or Video. It says File, whatever the declared type. Ogg is classified as Audio. Browsers' `MediaRecorder` makes WebM/Opus in Chrome and Edge and Ogg/Opus in Firefox; Safari makes MP4 (not tested here).

**Plan impact:** yes, task 14c. A recorded voice message can't rely on `metadata.type === 'Audio'` for WebM. Either recognise voice messages by a filename convention (and `content_type` `video/webm`) and render them with an audio player, or convert to Ogg/Opus before upload. The file name should carry the marker. Also store the duration somewhere other than Autumn's metadata (it doesn't give one for File).

### 8. CodeMirror and Ctrl-Alt-Arrow

Yes. `@codemirror/commands` 6.11.1 `defaultKeymap` has `Mod-Alt-ArrowUp` (addCursorAbove) and `Mod-Alt-ArrowDown` (addCursorBelow); Mod is Ctrl on Windows and Linux, Cmd on macOS. It also binds `Alt-ArrowUp/Down` (move line) and `Shift-Alt-ArrowUp/Down` (copy line). The composer (`apps/web/src/lib/composer/editor.ts`) spreads the whole `defaultKeymap`, so all of these are live there. The plan's capture-phase listener has to stop the event before CodeMirror sees it, for Alt+Arrow and Ctrl+Alt+Arrow alike.

**Plan impact:** no, as long as the registry listener runs in capture phase and calls `preventDefault` and `stopPropagation`.
