## Task 1: probes

Run on the local stack, 2026-10-16, on a throwaway server (`m47-probe`) owned by `dev-admin`, with `tuuli` as the target, `onni` as a Moderator and `dev` as a plain member. Nothing seeded was touched. The scripts are `tools/live/src/probe-moderation.ts` (API side) and `tools/live/src/probe-voice.ts` (calls in browsers, with `livekit-admin.ts` reading each participant's permissions from LiveKit itself).

### Move

`onni` moves `tuuli`, who is in Alpha, to Beta with `voice_channel`.

- **The target receives**, in this order: `ServerMemberUpdate` (+40 ms), `UserMoveVoiceChannel` with the node, `from`, `to` and a token (+65 ms), then `UserVoiceStateUpdate` for the old channel with `is_publishing: false`.
- **LiveKit removes her from the old room at about +170 ms**, with reason 4 (participant removed), the same reason as a kick. The only difference from a kick is the `UserMoveVoiceChannel` event about 100 ms earlier, so that event is what marks a removal as expected.
- **Others see only the `UserVoiceStateUpdate`.** `VoiceChannelMove` is not sent until the target connects to the new room. No stale `VoiceChannelLeave` arrived.
- **A target who doesn't follow stays a ghost.** With no handler, Stoat kept her listed in Alpha for over a minute, though both LiveKit rooms were empty. Following the move, or the fallback join, is what clears it.
- **A reconnecting target gets the event late, not lost.** With her network cut for 4 s, the move event arrived when it came back, about 2.5 s after the move, inside the token's 10 s life. A longer cut would outlive the token.
- **The move PATCH costs one slot** of the `/servers/…` bucket (5 per 10 s). Pacing is what makes several moves in a row slow.

### Server mute and deafen

`onni` sets `can_publish` or `can_receive` on `tuuli`. Checked against LiveKit's own view of each participant.

| Moderator is | Answer | Target's call | Moderator's call |
|---|---|---|---|
| In no call | 200 | Unchanged | Not in one |
| In another call | **500 InternalError**, though the member record changed and everyone got `ServerMemberUpdate` | Unchanged | Unchanged |
| In the same call | 200 | Unchanged: she keeps sending, her permissions stay full | Rewritten: `canPublishSources` becomes empty, which LiveKit reads as unrestricted, so nothing is actually blocked. `UserVoiceStateUpdate` names the moderator, with `is_publishing: true` |

So Stoat 0.15.5 does what the plan says: the flags are stored and announced, and nothing on the live call changes for the target. Deafen behaves the same way. Server-side enforcement isn't possible.

**Consequence for task 3:** a moderator in another call gets a 500 for an edit that succeeded. The client must not trust that status: treat the member update that follows as the result, and re-read the member before reporting a failure. Concord clients also ignore a `UserVoiceStateUpdate` for the moderator that comes from this bug.

### Disconnect

`remove: ["VoiceChannel"]` answers 200 and removes **the moderator** from the call, with `UserVoiceStateUpdate` and `VoiceChannelLeave` for them. The target stays. Confirmed broken, as the plan says. Not offered.

### Timeout in a call

A timed-out member keeps sending and hearing in a live call (12.0 kB/s before and 11.9 kB/s after, LiveKit permissions unchanged). Stoat only refuses a new join: `join_call` answers `403 MissingPermission`.

**Consequence:** a timeout doesn't silence a call. Added to task 6 as a Concord-side rule: a client whose own member is timed out leaves the call, as "can only read" implies.

### Ban with deletion

`PUT /servers/{s}/bans/{u}` with `delete_message_seconds: 3600` deleted the banned user's 3 recent messages in 18 ms, and left the owner's message. It needs only Ban members, so "server admins only" holds in Concord's client alone, as decision 6 says.

### Ranks and the owner

- **Rank decides** nickname changes, timeouts, kicks, bans and role giving. Against a member ranked above, a Moderator gets `403 NotElevated` for every one of them. Against a member ranked below, all succeed.
- **The owner with no roles ranks below every role.** A Moderator can change or remove the owner's nickname, and give them a role ranked below the Moderator. A Moderator can't kick or ban the owner (`400 InvalidOperation`) or time them out (`403 IsElevated`). Concord's `canActOnMember` already puts the owner out of reach, so the client never offers it; only direct API use can.
- **The owner passes their own rank checks**: with no roles they changed a Moderator's nickname.
- **Timeout has a second rule, separate from rank:** a target who holds Time out members can't be timed out by anyone, the owner included (`403 IsElevated`). **Consequence for task 6:** the Time out item is offered only for targets without that permission.
- **Giving a role** the giver ranks at or below fails with `403 NotElevated`.

### Without permissions

| Missing | What happens |
|---|---|
| Read message history | `GET` messages answers `403 MissingPermission`, search too. Sending still works |
| Connect | `join_call` answers `403 MissingPermission` |
| Speak | The token lists `camera`, `screen_share` and `screen_share_audio`, not `microphone` |
| Video | The token drops `camera`, `screen_share` and `screen_share_audio` |
| Speak and Video | The token's source list is **empty, which LiveKit treats as unrestricted**: the member can publish anything. Matches architecture 5.4 |
| Listen | `join_call` works, the token carries `canSubscribe: false`, so the member joins and hears nothing. Enforced by LiveKit |

**Consequence for task 5:** Listen, Speak and Video can all be told from the permissions the client already computes. Without Speak and Video the client has to stop the microphone and camera itself, since the server won't.

### Audit log

Each entry has `_id`, `server`, `reason`, `user` (who acted), `target` and `action`. The `X-Audit-Log-Reason` header lands in `reason` for deletions, bulk deletions, member edits, kicks and bans. The `type` filter works. A plain member gets `403 MissingPermission`.

| Action | Recorded |
|---|---|
| Message deletion | `MessageDelete` with the author and channel. Own messages aren't logged |
| Bulk deletion | `MessageBulkDelete` with the channel and a **count only** |
| Timeout set | `MemberEdit` with `after.timeout` |
| **Timeout removed** | `MemberEdit` with `before: {}` and `after: {}`. **Nothing says it was a timeout** |
| Server mute, deafen | `MemberEdit` with `can_publish` and `can_receive` before and after |
| Nickname | `MemberEdit` with `after.nickname` |
| Role given | `MemberEdit` with the role list before and after |
| Kick, ban, unban | `MemberKick`, `BanCreate`, `BanDelete`, each with the user |

**Consequence for task 8:** an empty `MemberEdit` should be shown as "edited a member", not hidden. A timeout's end can't be recovered from the log.

### Needs to be known for the next tasks

- **Probes leave no trace.** Each run deletes its server, and a later run first removes any left over.
- **Calls in one browser process stall after the first call ends**, on the local stack only: the next connection reaches LiveKit's signalling and never finishes ICE. The same Docker Desktop UDP quirk as in the handoff. Call checks that join twice should start a fresh browser per scenario, as `probe-voice.ts` does.
- **Chromium learns to filter the fake microphone** within a minute, so send rates read after that are low. Compare rates early in a call.

## Task 2: following a move

Built:
- **The event.** `UserMoveVoiceChannel` is decoded to a `voiceMoved` event (`packages/stoat/src/events.ts`). The store ignores it: the sidebar changes with the `VoiceChannelMove` that Stoat sends once the user has connected. `Session.onVoiceMoved` hands it to the voice controller.
- **The controller** (`apps/web/src/lib/voice/controller.svelte.ts`) follows it: it connects to the new room with Stoat's token, with no `join_call`, keeping mute, deafen and volumes, since those live in the controller. The old call's removal is dropped by the generation counter, so it never reads as "Disconnected".
- **The decisions** are pure and tested: `move.ts` (token life, whether a move concerns this call) and a `moved` step in the rejoin machine (`rejoin.ts`). A removal that reaches the client before the event is still followed, but only while the token is fresh, so a kick is never undone.
- **Fallback.** A token that is too old, or that LiveKit refuses, falls back to an ordinary join to the new channel (`join_call` with `force_disconnect`, which also clears the stale state).
- **The toast** says "You were moved to Beta." The plan wanted who moved her too, but Stoat's event doesn't name the moderator, and the audit log needs a permission members lack, so the name is left out.
- **No sound** plays for a move.

**Live check** `tools/live/src/voice-move.ts`, on a throwaway server, 2026-10-16, all passed:
- One move: followed in 2.2 s with no click, 10.8 kB/s sent afterwards, 0 extra `join_call`, her row in Beta for another member and gone from Alpha, the panel never says "Disconnected".
- Moves back to back, each sent once she was connected in the last place: all followed, 0 `join_call`.
- Mute and deafen set before a move survive it, and she sends 116 B/s.
- A move made while her connection was cut was followed once it returned, and she sent audio again.

**A limit of Stoat's, found by the check:** a second move sent *before* the first has connected is refused with `500 InternalError` (`voice_client.rs:151`), since the target is already out of the old room. The first move stands and the call follows it. The drag-and-drop in task 3 must therefore treat a move as pending until the person shows up in the new channel, and refuse a second one for them meanwhile (the plan already shows a pending state on the row).

## Task 6: text moderation

**Probes first**, on a throwaway server, about slow mode:
- `PATCH /channels/{c}` takes `slowmode` from 0 to 21,600 s; 21,601 is `FailedValidation`. Everyone in the channel gets `ChannelUpdate` with it.
- A message sent too soon gets **`429 {"type":"InSlowmode","retry_after":5}`**, the wait in seconds, on the sender's own message bucket. The owner bypasses it; a Moderator without Bypass slow mode doesn't.
- After each message sent, and each one refused, the sender alone gets **`UserSlowmodes`** with `{channel_id, duration, retry_after}`. These are "Stoat's own slow mode events".
- **A bug this found**: the REST client treated InSlowmode as a rate limit and retried every 5 ms (it read seconds as milliseconds) for up to a minute. It now throws it, and the composer counts the wait down instead.

Built:
- **Time out ›** in a member's menu and the moderation panel, after Open in moderation view: 1 minute, 5 minutes, 10 minutes, 1 hour, 1 day, 1 week, then Remove timeout while one runs. Each length opens a confirmation with a reason. It is offered only over someone below you who doesn't hold Time out members, read as if their own timeout had ended (`members.ts`, tested in `members.test.ts`).
- **A clock** beside a timed-out name in the member list and on messages, with the end as its tooltip, gone by itself at the end (`TimeoutMark.svelte`).
- **Leaving the call**: a client whose own member is timed out leaves its call and says so.
- **Slow mode** in a channel's settings, Off to 6 hours in Discord's steps, voice channels' chat included. The composer shows a timer with the rule as its tooltip, and while waiting the seconds left; Enter does nothing until then. The wait starts at once on sending and follows `UserSlowmodes` (`store.slowUntil`). Bypass slow mode, and the owner, see none of it.
- **Ban** gains "Delete their messages from the last" none, 1 hour, 24 hours or 7 days, for server admins only (`isServerAdmin`: the owner, or Manage server with Manage messages).

**Fixed after the pre-deploy review** (unit test for the reason only, live checks skipped at Jaakko's instruction):
- The reason went raw into `X-Audit-Log-Reason`, and browsers throw on a newline or any character past U+00FF, so a reason with "—", "€", an emoji or curly quotes failed the whole kick, ban, timeout, mute or move. `packages/stoat/src/reason.ts` now makes it one line and percent-encodes everything outside printable ASCII, `%` included; the audit log decodes it, so Finnish reasons survive. A reason that can't be encoded is left out, never failing the action. A ban still sends the raw reason in its body too, for the ban list.
- The composer's slow mode wait started before the send and was never taken back, so one failed send could lock it for up to 6 hours. A send that fails for any reason but InSlowmode now clears it (`session.send` resolves to the failure's type).
- Clearing slow mode (`clear: ["Slowmode"]`) now turns it off in the client.

## Task 9: reports

Built, in Concord's layer:
- **The store**: migration `005-reports.sql`. Each report keeps who reported what, when, the reason from a short list (spam, harassment, hate speech, sexual content, violence, something else) and optional notes. For a message it also keeps a copy of its text, as evidence, the one exception to the layer's rule of storing no Stoat data. The copy is dropped 90 days after the report closes, checked on every read.
- **Filing** (`POST /app/api/v1/reports`): the layer reads the channel and message from Stoat **as the reporter**, so only what they can see can be reported, and the author comes from Stoat, not the client. Own messages and own accounts are refused, and each person may file 10 reports an hour.
- **Who sees them** (`reports.ts`): a message in a server channel goes to that server's members with Manage messages; a DM or group message, or a person, goes to the admins on `ADMIN_USER_IDS`. Reports about the caller never show to them, so the reported person never learns who reported them, even as a moderator. Closing takes a note and checks the same access; someone without it gets 404.

## Task 13: upstream

The pull request text for Stoat, for Jaakko to file, or to ask an agent to. The line numbers are from the plan's source read of v0.15.5 (commit `dc31dd7`), and the code below is a sketch of each change rather than a tested patch. Whoever files it should check it against the file, build it, and run the reproduction on a local stack first, as M4.5's January pull request was.

> **Title**: Voice moderation acts on the moderator instead of the target
>
> **What happens**: in `crates/delta/src/routes/servers/member_edit.rs`, server mute (`can_publish`), server deafen (`can_receive`) and disconnect (`remove: ["VoiceChannel"]`) update the live call of the user making the request, not the member being edited:
> - lines 297–311 pass `&user`, the caller, to `sync_user_voice_permissions`,
> - lines 315–321 pass `&user` to `remove_user`.
>
> The database write at line 226 is for the right member, and the move branch (lines 242–291) already uses `target_user` throughout, so only these calls are wrong.
>
> **How to reproduce** (0.15.5, a server with two voice channels):
> 1. A member joins a voice channel; a moderator with Mute members joins the same one.
> 2. The moderator sets `can_publish: false` on the member. The member keeps publishing; LiveKit shows the **moderator's** permissions rewritten (`canPublishSources` becomes empty).
> 3. With the moderator in another call, the same edit answers `500 InternalError`, though the member record changed and `ServerMemberUpdate` went out.
> 4. `remove: ["VoiceChannel"]` disconnects the moderator, and the member stays.
>
> **The fix**:
> ```rust
> // member_edit.rs, mute and deafen (around lines 297–311)
> - sync_user_voice_permissions(db, voice_client, &user, &server, ...).await?;
> + sync_user_voice_permissions(db, voice_client, &target_user, &server, ...).await?;
>
> // member_edit.rs, disconnect (around lines 315–321)
> - voice_client.remove_user(&user.id, &channel_id).await?;
> + voice_client.remove_user(&target_user.id, &channel_id).await?;
> ```
> The 500 for a moderator in another call should go with it, since it comes from looking up the caller's room. If the target isn't in a call, both should be no-ops that answer 200.
>
> **Two related problems, which could be the same PR or follow-ups**:
> 1. **Deafen isn't reported.** `sync_user_voice_permissions` (`crates/core/database/src/voice/mod.rs`, lines 468–555) sends `UserVoiceStateUpdate` with `is_publishing` but never `is_receiving`, so other clients can't show a server deafen without reading the member. It should set `is_receiving` from the new `can_receive`.
> 2. **No Speak and no Video means no restriction.** The token (`crates/core/database/src/voice/voice_client.rs`, lines 87–98) lists allowed sources from Speak and Video. With neither, the list is empty, and LiveKit reads an empty `canPublishSources` as "anything", so the member can publish a microphone and a camera. With neither permission, the token should set `canPublish: false` instead of an empty source list.
>
> **Also seen, not fixed here**: a second move sent before the first has connected answers `500` (`voice_client.rs:151`), since the member has already left the old room. A clearer error, or treating the move as from wherever the member is now, would help clients.
>
> Checked against the main branch (0.16.0): the member_edit bug is unchanged there, and no issue or pull request for it was found.

**Once a release has it and our stack runs it**: add Disconnect to the participant menu, and drop the client-side enforcement notes from server mute and deafen, since the server then enforces them too. Concord's own enforcement can stay as a second layer.
