## Task 1: probes, 2026-10-15

On the local stack, with throwaway scripts in the scratchpad.

| Question | Answer |
|---|---|
| **Mark unread**: does Stoat accept an acknowledgement that moves backwards? | Yes. `PUT /channels/{id}/ack/{message}` with an older message moves the channel's `last_id` back, and the account's other devices get a `ChannelAck` with the older ID. So "Mark unread" acknowledges the message before the one clicked. |
| **Mark a server read**: does `PUT /servers/{id}/ack` clear every channel? | Every channel that can be unread. Each of the 8 text channels with messages got a `ChannelAck` on the other device. The 2 voice channels were left alone, but their only messages are "call started" notices, which don't set `last_message_id` and so are never unread. |
| **A pasted `giphy.com` link** | January gives the page link (`giphy.com/gifs/…`) only a "Website" embed marked GIF, with no image or video, so it can't play. A direct media link, `media.giphy.com/media/{id}/giphy.gif` or `i.giphy.com/{id}.webp`, gets an Image embed with its size. **The picker sends direct media links.** |
| **GIPHY's terms**, researched by a Sonnet agent from developers.giphy.com | Against the plan. The docs' best practices say "Do not proxy requests to GIPHY, either API calls or media URL loads" and "All requests to GIPHY should be made directly from the client side", and media "should not be cached, proxied, rewritten, or stored", except with written approval. Beta keys allow 100 calls an hour. A production key needs an application, and its price isn't published. |
| **Other GIF providers** | Tenor's API shut down on 2026-06-30, so Stoat's own `gifbox`, which only speaks to Tenor, is dead too. KLIPY, which Discord reportedly uses, has the same rule: server-side requests, proxying and media caching "require prior approval" from developers@klipy.com. Its test keys allow 100 requests an hour, and production keys are unlimited once it has seen KLIPY's branding, a "Search KLIPY" placeholder. Third-party write-ups say they are free, which KLIPY's own pages don't state. |
| **Send-side bandwidth estimation** | No help, so not proposed. With `use_send_side_bwe` on the local LiveKit, `share.ts` ran twice. In the first run the viewer's downlink squeeze cut the frames entirely, and both browsers lost their connection and reconnected. In the second, the viewer dropped to 360p as before, and 1080p still hadn't come back 67 s after the squeeze ended. The upload case recovered in 4 to 5 s either way, as without it. The setting is off again. |

**Decision needed from Jaakko for task 7**: both GIF providers want members' browsers to talk to them directly. The plan's privacy design, with searches and images through our own server, needs a provider's written approval. The options are in the task 7 section below, once decided.

## Task 2: message, link and image menus, 2026-10-15

**Built**:
- **Right-click on a message**: four quick reactions, the most used first and then 👍 ❤️ 😂 😮, and "Add reaction". Then Edit, Reply, Pin, Mark unread, Copy text, Copy message link and Copy message ID, each only when allowed, and Delete.
- **On a link**: Open link and Copy link are added. **On an image or GIF**: Copy image, Save image and Open original.
- **Keyboard**: one message at a time is reached by Tab, Up and Down move between messages, and the context-menu key or Shift+F10 opens the menu at the focused message. A message in the middle of an edit, and selected text, keep the browser's own menu, for spelling and copying.
- **Mark unread** moves this device's read point to just before the message, tells Stoat, and shows the "new messages" line there. The open channel doesn't read itself again until it is left or the account sends there. Another open device takes it up the next time it starts.
- **Copy and save** read the image as shown, through Stoat's file server or January, so no third party sees the request. Copying turns a GIF into a still PNG, the only image type browsers put on the clipboard.

**Check**: `tools/live/src/menus.ts` passed twice in a row on the local stack. It covers each item's result through the UI or the API, the link and image items, both keys and Down, and Mark unread holding for 3 s while open.

**Found while checking**: a nested element's menu, such as the author's name inside a message, now wins over the message's own.

## Task 3: server menu and the tab's title, 2026-10-15

**Built**:
- **"Mark as read"** comes first in the server icon's menu while anything in the server is unread or mentions you.
- **The tab's title** counts what the rail's badges count, mentions in servers plus unread DMs and friend requests, as `(3) Concord`. Plain unread channels don't count, as on Discord.

**Found: Stoat's server-wide acknowledgement misses messages from the last few seconds.** `PUT /servers/{id}/ack` acknowledges each channel's newest message as Stoat last recorded it, and Stoat records it 5 to 8 s after the message, measured four times. A server marked read in those seconds answered 204 but stayed unread. Worse, a channel just read on this device could move back by one. So the client acknowledges the server first, then acknowledges each channel whose newest message is under 15 s old on its own, with the message it knows.

**Check**: `tools/live/src/server-read.ts`, with `dev` on two devices. Marking the server read on one cleared the other in 63 ms, title included, and Stoat had both channels read up to messages sent seconds before. A read server doesn't offer "Mark as read".

## Task 9: upstream, January and the Instagram embed fixers, 2026-10-15

**The pattern today**, read from the `ghcr.io/stoatchat/proxy:v0.15.5` image's binary, from `crates/services/january/src/requests.rs`. January fetches hosts that match it as Discord's crawler, and every other host as itself:

```
^(?:(?:vx|fx)?twitter|(?:fixv|fixup)?x|(?:old\.|new\.|www\.)reddit)\.com|klipy\.com
```

**Tested**: the proposed pattern below matches the six fixer hosts, with and without `www.`, and matches 15 other hosts exactly as the current one does. Those include `instagram.com` itself, which stays unmatched, bare `reddit.com`, which the current pattern doesn't match either, and lookalikes such as `xkkinstagram.com`. The test was a throwaway Node script. JavaScript's regular expressions agree with Rust's `regex` crate for everything in this pattern.

**Pull request text**, for Jaakko to file at github.com/stoatchat/stoatchat, or to ask an agent to:

> **January: fetch Instagram embed fixers as Discord**
>
> Sites such as kkinstagram, ddinstagram and instagramez exist to give Instagram links a playable preview in chat apps. They serve the video and its Open Graph tags only to crawlers they recognise, as January already knows from fxtwitter and vxtwitter. Fetched as January, they return no media, so a pasted fixer link shows no preview.
>
> This adds them to the hosts January fetches with Discord's user agent, in `crates/services/january/src/requests.rs`:
>
> ```diff
> -^(?:(?:vx|fx)?twitter|(?:fixv|fixup)?x|(?:old\.|new\.|www\.)reddit)\.com|klipy\.com
> +^(?:(?:vx|fx)?twitter|(?:fixv|fixup)?x|(?:old\.|new\.|www\.)reddit|(?:www\.)?(?:kk|dd)instagram|(?:www\.)?instagramez)\.com|klipy\.com
> ```
>
> `instagram.com` itself is unchanged. Every host the pattern matched before still matches, and nothing new does apart from the six fixer hosts, with and without `www.`.
>
> Separately, and not changed here: the pattern has no `$`, and `klipy\.com` has no `^`, so hosts such as `twitter.com.example.net` and `evilklipy.com` are also fetched as Discord. Anchoring both ends of the alternation would fix that, if wanted.

**Our side**: nothing changes in Concord. Once January has it, fixer links preview and play like fxtwitter links do now.

## Task 10: server tags, 2026-10-15

The first feature on Concord's own layer.

**Built**:
- **The store**: migration 2 adds a server's tag, up to 4 letters or digits with one of the server's custom emoji as the badge, and which tag each user wears. Disabling a tag removes it from everyone wearing it.
- **The API**, under `/app/api/v1/tags`:
  - `POST lookup` with up to 1,000 user IDs, a read, so a member list costs one request,
  - `GET servers?ids=`, a read,
  - `PUT` and `DELETE servers/{server}`, only for someone on Stoat's server-creator list who holds Manage server there. The badge must be that server's own emoji, which the layer asks Stoat about.
  - `PUT me` with `{ server }`, only for a member of that server, or `{ server: null }`.
- **The client** fetches tags at sign-in, every 60 s and when the window regains focus. It shows a tag only for someone it knows to be in the tag's server.
- **Shown** next to the name in messages, the member list, the DM list and the profile card. A click on it in messages or the profile card shows which server it's from.
- **Settings**: "Server tag" in server settings for those allowed, with the tag, a badge picked from the server's emoji, a preview, Save and Disable. "Server tag" in profile settings lets a member choose any tag of a server they're in, or none.

`layer.ts` still passes against the migrated store.

## Task 7: GIF picker, decided: favourites only, no search

**Jaakko's decision, 2026-10-15**: favourite GIFs as on Discord, with no search built in. So no GIF service is contacted, and no key is needed. The options as they were put:

Task 1 found that both GIF providers forbid the planned design, with searches and images through our own server, unless they approve it in writing. The options:

| Option | What members' browsers do | Cost |
|---|---|---|
| **A. KLIPY, straight from the browser** (recommended) | They call KLIPY's API and load its images while the GIF tab is open. Sent GIFs are links, which Stoat's January embeds as it does now, so receivers never contact KLIPY. | The key is in the client, as KLIPY intends. A test key allows 100 requests an hour for everyone. A production key is unlimited once KLIPY has seen its branding, a "Search KLIPY" placeholder. |
| B. Ask KLIPY or GIPHY to approve our proxy | Nothing, as planned. | An email, and a wait with no promised answer. It could follow A later. |
| C. No picker | Nothing. Pasted GIF links already play. | Members find GIFs elsewhere. |

GIPHY's version of A is the same, except that the beta key is capped at 100 calls an hour and its production pricing isn't published. KLIPY is the better fit, and January already fetches `klipy.com` as Discord.

With A, opening the GIF tab is what reveals a member's address to KLIPY, and a line in the tab can say so.

## Review of the session's diff, 2026-10-15

A Sonnet review of `e06c65f..HEAD`, read-only. Nothing security-class: the tag endpoints check every ID, gate and membership, and their SQL is parameterised. It found these, all fixed:

- **A watched stream's tile vanished** while its subscription was on its way, and stayed gone if the subscription failed. The tile now stays, and a failed subscription brings back its Watch button.
- **A full reconnect forgot which streams were watched**, because LiveKit unpublishes every track while it restarts. They now stay watched through a reconnect, and only streams that really ended are forgotten.
- **Losing Speak and gaining it again in one call** left a dead microphone, and a failed publish left the capture open. The microphone now closes when it's unpublished or fails to publish, and a refused microphone isn't asked for again in that call. `voice-channel.ts` now checks Speak lost and gained again: 0 B/s, then about 12,000 B/s, with no rejoin.
- **On Android, a long press on an author's name** opened the message's menu over theirs. The name's menu now keeps it.
- **"Open original" could open any address a sender put in an embed**, such as `javascript:`. Only web addresses are opened now.
- **"Mark unread" on the first loaded message** of a partly loaded history fell back to a local-only mark. It isn't offered there now.
- **Focused messages** read only the author's name to screen readers, and nothing for a grouped message. They now read the name and the text. The message Tab reaches is worked out once, skipping system lines.
- **"Mark as read" for a server**, if Stoat refused it, looked done but wasn't. Each channel now goes through the usual acknowledgements and their retries instead.
- **Smaller fixes**: the server tag settings ignore a late answer for another server, and the tag lookup asks about at most the 200 servers its endpoint takes.

**Left, noted**:
- Firefox keeps Ctrl+Shift+M for its responsive design mode, and Chrome may keep it for its profile menu. The buttons stay the way there.
- A tag's badge breaks if its emoji is deleted from the server.
- Only someone on the server-creator list can disable a server's tag, the same gate as enabling it.
- Anyone signed in can look up which tag a user wears.

**Caught before handing over**: the new microphone handler also fired while LiveKit restarts a connection, when the SDK unpublishes our tracks to publish them again. So after a restart the microphone stayed silent, and `voice-restart.ts` failed. The microphone is now closed on an unpublish only while connected. `voice-restart.ts` passes again, with both back in 7 to 8 s, and `voice-channel.ts` still passes.

All the checks this session touched pass again: `menus`, `server-read`, `voice-controls`, `voice-channel`, `tags`, `share`, `voice`, `voice-restart`, `callview` and `dm-call`. Run back to back locally, they can spend the layer's per-address limit, because every local request comes from Docker's one address, so `tags.ts` waits out an address 429.
