## Task 1: probes, 2026-10-15

On the local stack, with throwaway scripts in the scratchpad.

| Question | Answer |
|---|---|
| **Mark unread**: does Stoat accept an acknowledgement that moves backwards? | Yes. `PUT /channels/{id}/ack/{message}` with an older message moves the channel's `last_id` back, and the account's other devices get a `ChannelAck` with the older ID. So "Mark unread" acknowledges the message before the one clicked. |
| **Mark a server read**: does `PUT /servers/{id}/ack` clear every channel? | Every channel that can be unread. Each of the 8 text channels with messages got a `ChannelAck` on the other device. The 2 voice channels were left alone, but their only messages are "call started" notices, which don't set `last_message_id` and so are never unread. |
| **A pasted `giphy.com` link** | January gives the page link (`giphy.com/gifs/…`) only a "Website" embed marked GIF, with no image or video, so it can't play. A direct media link, `media.giphy.com/media/{id}/giphy.gif` or `i.giphy.com/{id}.webp`, gets an Image embed with its size. **The picker sends direct media links.** |
| **GIPHY's terms**, researched by a Sonnet agent from developers.giphy.com | Against the plan. The docs' best practices say "Do not proxy requests to GIPHY, either API calls or media URL loads" and "All requests to GIPHY should be made directly from the client side", and media "should not be cached, proxied, rewritten, or stored", except with written approval. Beta keys allow 100 calls an hour. A production key needs an application, and its price isn't published. |
| **Other GIF providers** | Tenor's API shut down on 2026-06-30, so Stoat's own `gifbox`, which only speaks to Tenor, is dead too. KLIPY, which Discord uses, has the same rule: server-side requests, proxying and media caching "require prior approval" from developers@klipy.com. Its test keys allow 100 requests an hour, and production keys are free and unlimited once it has seen KLIPY's branding, a "Search KLIPY" placeholder. |
| **Send-side bandwidth estimation** | No help, so not proposed. With `use_send_side_bwe` on the local LiveKit, `share.ts` ran twice. In the first run the viewer's downlink squeeze cut the frames entirely, and both browsers lost their connection and reconnected. In the second, the viewer dropped to 360p as before, and 1080p still hadn't come back 67 s after the squeeze ended. The upload case recovered in 4 to 5 s either way, as without it. The setting is off again. |

**Decision needed from Jaakko for task 7**: both GIF providers want members' browsers to talk to them directly. The plan's privacy design, with searches and images through our own server, needs a provider's written approval. The options are in the task 7 section below, once decided.
